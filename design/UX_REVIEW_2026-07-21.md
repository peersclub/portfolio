## Prioritized Findings

### CRITICAL

**1. `captain-fresh-old` and `captain-fresh-2` create real, user-visible duplication — not just orphaning**
- `src/data/projects.ts:71-85` defines a `captain-fresh-old` project ("CaptainFresh (Legacy)") with **no `cover`/`category`** field.
- `src/components/HorizontalProjects/HorizontalProjects.tsx:9` correctly filters the home gallery to `p.cover && p.category`, so the home page shows 6 clean projects.
- But `src/app/projects/page.tsx:100` (`{projects.map(...)}`) iterates the **raw, unfiltered array** — so the "Work" nav destination shows **7 cards**, and a visitor scrolling the horizontal timeline sees both "CaptainFresh" (2021-2024, "Impact: Industry First / Scale: Global") and "CaptainFresh (Legacy)" (same years, **identical metric labels/values**) back to back.
- Separately, `src/app/projects/captain-fresh-2/page.tsx` is a standalone route (not part of the `[slug]` system, no entry in `projects.ts`) that renders `<CaptainFreshStory />` — **the exact same component** rendered by `/projects/captain-fresh` (see `src/app/projects/[slug]/page.tsx:94-96`). It is a byte-for-byte duplicate page at a different URL, linked from nowhere, indexable by search engines.
- **Impact:** A peer/founder doing due diligence (the case-study journey) hits visible, unexplained duplication in the primary portfolio artifact — this is the single most credibility-damaging structural issue on the site.
- **Fix:** Delete `src/app/projects/captain-fresh-2/` entirely. Either remove `captain-fresh-old` from `projects.ts` or give it a distinct narrative framing ("earlier concept exploration") and exclude it from `/projects/page.tsx`'s map the same way the home gallery does (filter by `cover`/`category`, or add an explicit `archived: true` flag and filter it out of both listings, reachable only via direct link from within the main CaptainFresh case study as a "see also" if truly worth keeping).

**2. `/projects` (the "Work" landing page) hides the mouse cursor with no replacement**
- `src/app/projects/page.tsx:184-187` and `:260`: `.sticky-viewport, .projects-page-wrapper { cursor: none !important; }` / `.card-link { cursor: none; }`.
- `src/components/HorizontalProjects/HorizontalProjects.tsx:253` also sets `cursor: none`.
- Grepped the entire codebase for a custom-cursor implementation (`CustomCursor`, `data-cursor-text` consumer, cursor-follower component) — **none exists**. The only reference to `data-cursor-text` is documentation on the orphaned `/design` page (`src/app/design/page.tsx:281,296-299`) describing a cursor system that was apparently never built or was removed.
- **Impact:** On the page most likely to be a recruiter's or peer's very next click after landing, the pointer becomes invisible on non-touch devices, with only GSAP scroll-hijacking to navigate. This is a severe, first-impression-breaking anomaly (Nielsen #1 Visibility of System Status — the user loses the most basic system status indicator, their own cursor).
- **Fix:** Either implement the intended custom cursor (dot/label follower) or remove all three `cursor: none` declarations immediately.

**3. Stale, hardcoded gold branding (`#E8C547` / `rgba(232,197,71,…)`) is baked into 61+ places across live pages, not just `/design`**
- `grep` count: 61 occurrences of the old gold token across `src` (verified via `grep -rn "232, 197, 71\|#E8C547" src --include="*.tsx"`), including production case-study layouts (e.g., `AssetWorksLayout.tsx:27,36,71,79` hardcodes `#E8C547` directly rather than `var(--accent)`) and `StickySubNav.tsx:109` (`rgba(232, 197, 71, 0.1)` for the active-tab background, used on `/resume`, `/playbook`, `/therightfit`).
- The site ships 8 selectable themes (`midnight, ocean, sunset, forest, lavender, ember, monochrome, light` — `src/app/layout.tsx:63`) via `ThemeSwitcher`. Any hardcoded gold value **will not react to theme changes**, so switching themes produces a visibly broken/inconsistent accent color on exactly the pages that most need to look polished (case studies, the shared sub-nav pattern).
- `/design` itself (`src/app/design/page.tsx:29`) documents `--accent: #E8C547` as current truth, but this is presented as the design system's source of truth while the rest of the app has since diverged / never fully adopted CSS variables.
- **Impact:** compounds Finding 5 below — the "system" page is not just internally stale, it's actively contradicted by the live app's own selectable-theme feature.
- **Fix:** Replace all hardcoded hex/rgba gold literals with `var(--accent)` / `var(--accent-subtle)` tokens; treat this as a pre-req for any `/design` rebuild.

### HIGH

**4. `HERO_NAV_LINKS` is dead code that misrepresents the actual home-page nav**
- `src/data/navigation.ts:17-20` filters `NAV_LINKS` down to 5 items (drops `/therightfit` and `/contact`) specifically for the hero.
- `src/app/page.tsx:12,31` imports and passes this as `navLinks` into `<MinimalistHero>`.
- But in `src/components/ui/minimalist-hero.tsx`, the `navLinks` prop is destructured (line 43) and **never rendered** — the `NavLink` helper component (line 24) is defined but never invoked anywhere in the file. There is only a `{/* Spacer for global nav */}` div (line 61), confirming the intent is for the global fixed `<Navigation>` (7 links, rendered once in `src/app/layout.tsx:73`) to be the only nav visible.
- **Net effect for users:** there is no actual "condensed 5-link hero nav" bug in production — the single global nav is consistently present site-wide, which is good. But the **codebase itself is misleading**: `HERO_NAV_LINKS` looks like live, intentional IA (a deliberately reduced nav for first impression) when it's actually inert, unused plumbing.
- **Fix:** Either delete `HERO_NAV_LINKS` and the unused prop/component code, or actually wire it up if a condensed hero nav was the original intent. Don't leave IA-shaped dead code in `navigation.ts` — the next person who edits nav (including a future review) will reasonably assume it does something.

**5. Two structurally orphaned routes, `/network` and `/design`, are fully built pages with no in-app path to them**
- `/network` (`src/app/network/page.tsx`) renders an "Interactive LinkedIn knowledge graph — 11,658 connections" — a substantial, purpose-built feature with zero discoverability. It's plausible this is an intentional Easter egg/share-link page, but as-is it reads as an abandoned feature.
- `/design` (`src/app/design/page.tsx`) is an internal design-token explorer that is (a) stale (Finding 3) and (b) publicly deployed with no `noindex`.
- **Fix:** For `/network`: either link it from somewhere deliberate (e.g., a "My Life" or "Playbook" callout, or the sharing page) or gate it behind a query param/direct-share link if it's meant to be a private link-out asset, not a crawlable page. For `/design`: see Finding 6 below.

**6. Page-header / sub-nav pattern is inconsistent across the 8 non-orphan top-level pages**
Confirmed by direct comparison:
- `/resume`, `/playbook`, `/therightfit` share one real pattern: hero `<section>` with `motion.h1` → `<StickySubNav sections={...} />` → sectioned content with `scroll-mt-*` anchors → `<Footer />`. This is a genuinely good, repeatable template (`src/app/resume/page.tsx`, `src/app/playbook/page.tsx`, `src/app/therightfit/page.tsx`).
- `/sharing` and `/sharing/[slug]` share a *different but internally consistent* pattern: centered `page-header`/`mono-label` + card list, with `<Footer />` (`src/app/sharing/page.tsx`, `src/app/sharing/[slug]/page.tsx`).
- `/mylife` and `/contact` are one-offs with their own bespoke hero markup and `<Footer />` but no `StickySubNav` (arguably fine — single-scroll narrative pages — but there's no shared "PageHeader" component anywhere; every page hand-rolls its own `<h1>` block, meaning 5+ near-duplicate hero implementations to keep visually aligned over time).
- `/projects` breaks the pattern entirely: no `<h1>` matching the nav label ("Work"), no `StickySubNav`, **no `<Footer />` at all** (confirmed absent from `src/app/projects/page.tsx`), custom cursor-hiding GSAP scroll-hijack instead of native scroll.
- `/design` and `/network` also render with no `<Footer />` and no relation to the rest of the site's visual language.
- **Fix:** Extract a shared `PageHero`/`PageHeader` component for the hero+H1+subtitle block, and make `<Footer />` presence a hard rule for every top-level route (including `/projects`).

**7. Project case-study detail pages have zero shared "back navigation" or footer pattern**
- The `[slug]` router (`src/app/projects/[slug]/page.tsx:94-120`) branches to 7 different bespoke layout components, each of which reimplements its own "Back to Projects" link independently:
  - `StoryLayout.tsx:61-69` — pill-styled, `top-24`, `mix-blend-difference`.
  - `AssetWorksLayout.tsx:24-31` — plain text link, `top-0`, hardcoded `#E8C547` color (also Finding 3).
  - The generic fallback template (`src/app/projects/[slug]/page.tsx:125-128`) uses yet a third style (`fixed`, `top: 6rem`, glass pill).
- None of the 7 bespoke layouts (`AssetWorksLayout`, `CoinDCXLayout`, `CoxLayout`, `BabychakraLayout`, `KleverLayout`, `CaptainFreshLayout`, `CaptainFreshStory`) render the shared `<Footer />` — each ends in its own full-viewport CTA section instead. Once a visitor goes past `/projects` into any real case study, **the sitewide footer (social links, copyright, consistent close) disappears entirely** until they click back.
- **Impact:** Violates Nielsen #4 (Consistency and Standards) — "back" affordance location/style changes per case study, and the site's one persistent trust/contact signal (Footer) vanishes on the pages a peer/founder is most likely to spend the longest time on.
- **Fix:** Extract one shared `<CaseStudyBackLink />` and require every case-study layout to end by rendering the shared `<Footer />` (or a shared case-study-specific "Next steps" strip that itself links to `/contact`).

**8. The generic case-study fallback template ships literal placeholder copy**
- `src/app/projects/[slug]/page.tsx:198-224` — for any project slug that reaches this fallback (i.e., any new project added to `projects.ts` without an accompanying `if (slug === '...')` branch at lines 94-120), the rendered page reads: *"Add your case study content here...", "Add Image / Screenshot / Video", "Add an important callout or quote here."*
- Currently dead (all 7 live slugs have explicit branches), but it's an unguarded landmine: adding an 8th project to `projects.ts` without also adding a branch will silently ship a placeholder page to production.
- **Fix:** At minimum, make the fallback visually marked as a draft/WIP state (e.g., a dev-only banner) or throw/log a build-time warning when a project lacks a matching branch.

### MEDIUM

**9. Minimal accessibility scaffolding — mobile menu, active-nav state, and heading hierarchy**
- Across the entire `src` tree, only **3** `aria-*` attributes exist: `Navigation.tsx:104` (`aria-label="Toggle menu"` on the hamburger), `ThemeSwitcher.tsx:60` (`aria-label="Toggle Theme"`), `projects/page.tsx:111` (`aria-label` on project card links).
- The mobile menu toggle (`Navigation.tsx:101-109`) is a disclosure pattern (button that opens/closes a panel) but has **no `aria-expanded`/`aria-controls`** — screen-reader users get no signal of open/closed state.
- The active nav link (`Navigation.tsx:78`, `.nav-link.active`) is communicated **only via color** (`color: var(--accent)`), with no `aria-current="page"` — fails "don't rely on color alone" (WCAG 1.4.1) and Nielsen #1 (visibility of system status) for assistive tech.
- No skip-to-content link exists anywhere (`grep` for `skip-link`/`SkipLink` returned nothing) — every page load forces keyboard users through the full nav before reaching content.
- `/network` (`KnowledgeGraph.tsx:349`) has **no `<h1>`** at all — its only heading is an `<h2>Network Atlas</h2>`, a hierarchy skip.
- One positive to note: `src/app/globals.css:800-803` defines a global `:focus-visible { outline: 1px solid var(--accent); outline-offset: 2px; }` — a real, working baseline focus indicator site-wide. Don't regress this.
- **Fix:** Add `aria-expanded`/`aria-controls` to the mobile toggle, `aria-current="page"` to the active nav link, a skip link in `layout.tsx`, and an `<h1>` to `/network`.

**10. `/design` nests a second `<main>` landmark and a second competing navigation system**
- Global layout already renders `<main className="relative z-10">` (`layout.tsx:74-76`) around all page content.
- `src/app/design/page.tsx:114` renders its own `<main className="main-content">` inside that — an invalid nested `<main>` landmark (screen readers expect one `main` per page).
- `design/page.tsx:90-111` also renders a second, independent fixed-position left sidebar nav (`position: fixed; top:0; left:0; height:100vh`, lines 314-325) that visually competes with the global fixed top pill-nav rendered by `Navigation.tsx` — two unrelated "here's how to navigate" affordances stacked on one page.
- **Fix:** Folds into the `/design` recommendation below — if rebuilt, it should use the site's actual layout/landmark conventions, not its own parallel shell.

**11. Footer copyright is a hardcoded stale year**
- `src/components/Footer/Footer.tsx:13` — `<span className="copyright">© 2025 Suresh Victor</span>` — hardcoded, already stale relative to the current date (2026-07-21).
- **Fix:** `{new Date().getFullYear()}` or a build-time constant.

### LOW

**12. Contact page's brand-color hover states are mouse-only**
- `src/app/contact/page.tsx:48-57` and `:76-85` set hover brand tint via `onMouseEnter`/`onMouseLeave` inline style mutation rather than CSS `:hover`/`:focus-visible`. The global `:focus-visible` outline still applies (so keyboard users get *a* focus indicator), but the richer WhatsApp-green/Gmail-red hover affordance that sighted mouse users see is invisible to keyboard-only users landing on the same buttons.
- **Fix:** Move to CSS `:hover, :focus-visible` selectors instead of JS-driven inline styles.

## User Journey Assessment

**Recruiter journey** (land → assess → download resume → contact)
- Works end-to-end. Home hero → "Read More" (`page.tsx:33`, links to `/resume`) → `/resume`'s `StickySubNav` "Get Resume" button correctly links to `public/resume.pdf` (verified the file exists on disk) → Contact is reachable via global nav or the in-page `<Contact />` section on home.
- Minor friction: the global nav is the *only* real nav (Finding 4), so a user who doesn't notice the top bar and only reads the hero's plain-text "Read More" link has one path to Resume and no visible path to Contact until they scroll the full home page or notice the top bar.

**Peer/founder journey** (projects → case study → contact)
- Breaks at Finding 1 (duplicate CaptainFresh entries visible in the primary timeline) and Finding 2 (invisible cursor on the entry point to this whole journey).
- Once inside a case study, Finding 7 means the trip back to a global "contact" affordance depends entirely on that case study's bespoke, inconsistent "Back to Projects" link — there is no persistent way to jump straight to Contact from inside a case study except AssetWorksLayout's one hardcoded `/contact` link (`AssetWorksLayout.tsx:76-80`); the other 6 layouts were not checked exhaustively for an equivalent, so likely inconsistent across case studies.

**Content journey** (sharing → resource → copy prompt)
- Cleanest journey on the site. `/sharing` → `/sharing/[slug]` has a real, consistent "All Resources" back link (`sharing/[slug]/page.tsx:82-86`), a working "Copy Full Prompt" button (`handleCopy`, lines 18-23), and a "not found" fallback state with its own back link (lines 26-52). No breakage found.

## Direct Answers to the Assessment Questions

1. **All 14 routes reachable?** No — `/design`, `/network`, `/projects/captain-fresh-2` are URL-only orphans; `/projects/captain-fresh-old` is reachable but shouldn't be surfaced the way it currently is (visible, unfiltered, near-duplicate of the main CaptainFresh entry). Labeling is consistent for "Work" → the `/projects` route only in the sense that the URL matches; the page's own H1 ("Innovating At Scale") never echoes "Work" or "Projects," so there's no textual confirmation loop for the user.
2. **Do `/resume`, `/playbook`, `/therightfit` share a pattern that others lack?** Yes, confirmed identical hero+StickySubNav+sectioned-content+Footer scaffold. No other route replicates it, and `/projects` diverges hardest (no Footer, no H1/nav-label echo, cursor-hidden scroll-hijack).
3. **Where do journeys break?** Recruiter journey: intact. Peer/founder journey: breaks at the duplicate-projects and cursor issues on entry, and loses a consistent path back to Contact once inside a case study. Content journey: no breakage found.
4. **Do the CaptainFresh duplicates confuse visitors?** Yes — concretely, `/projects` renders both "CaptainFresh" and "CaptainFresh (Legacy)" with identical metric copy, and `/projects/captain-fresh-2` is an unlinked, byte-identical duplicate of `/projects/captain-fresh`. Cleanest structure: one `/projects/captain-fresh` case study; delete `captain-fresh-2`; either delete `captain-fresh-old` or keep it only as an internal "earlier concept" link referenced from within the main case study, excluded from both project listings.
5. **What to do about `/design`?** Rebuild, but not before fixing Finding 3 — right now it would document colors the app doesn't consistently use. Recommended order: (a) sweep hardcoded gold → CSS vars sitewide, (b) decide if `/design` should be public (portfolio flex / prove design-systems thinking) or internal-only (`noindex`, not deployed, or gated locally) — given the user is a Product Architect, a *correct and current* `/design` page is actually a legitimate portfolio asset, but a stale one actively undermines the "systems thinker" positioning the rest of the site is going for. Don't leave it live in its current stale/duplicate-nav state.
6. **Accessibility basics.** Heading hierarchy is fine on most pages (one `<h1>` each) except `/network` (no `<h1>`). No skip link anywhere. Sparse aria usage (3 attributes sitewide) — the mobile menu disclosure and active-nav-link states are the two concrete, low-effort fixes. One genuine positive: global `:focus-visible` styling exists and works.

## Overall UX Score: 6/10

The three page templates that got real design attention (resume/playbook/therightfit) are genuinely well-structured and consistent. The score is pulled down by: user-visible content duplication in the primary "Work" journey (Finding 1), an invisible cursor on that same journey's entry page (Finding 2), a design system page that actively contradicts the live app's theming (Finding 3), and a footer that disappears for the entire back half of the peer/founder journey (Finding 7). None of these are cosmetic — they sit directly on the two journeys (recruiter, peer/founder) the site exists to serve.

**Overall Verdict:** Approved with Changes — ship-blocking items are Findings 1-3 (all Critical); everything else can be sequenced as fast-follow.

## Key Recommendations (top 3, actionable this week)

1. Delete `src/app/projects/captain-fresh-2/`; decide the fate of `captain-fresh-old` (drop or clearly re-frame + filter out of `/projects/page.tsx`'s unfiltered `.map`).
2. Remove the three `cursor: none` declarations (`projects/page.tsx:184-187,260`; `HorizontalProjects.tsx:253`) or ship the custom cursor that was evidently planned but never built.
3. Sweep the 61 hardcoded `#E8C547`/`rgba(232,197,71,…)` occurrences to `var(--accent)`/`var(--accent-subtle)` before touching `/design` at all — otherwise any `/design` rebuild will be stale again the moment it ships.

## Accessibility Status: Needs Improvement

Baseline focus-visible styling exists and works; missing `aria-expanded` on the mobile menu, missing `aria-current` on active nav state, no skip link, and one missing `<h1>` (`/network`) are all quick, well-scoped fixes.

## Notes

- Recurring pattern across this codebase: components consistently prefer inline `style jsx` blocks with hardcoded color literals over the CSS-variable theme system that clearly exists and is mostly well-designed (`globals.css` custom properties, 8-theme `ThemeSwitcher`). Any future component work should default to `var(--token)` and treat a hardcoded hex/rgba color as a review flag.
- `navigation.ts` currently exports one dead list (`HERO_NAV_LINKS`) alongside the live one (`NAV_LINKS`). Worth a repo-wide dead-code pass given this was found by accident while checking hero-nav rendering.
- The `/sharing` → `/sharing/[slug]` pair is the strongest structural template on the site (consistent header, card pattern, back-link, empty state) and is a reasonable reference to generalize from when building the shared `PageHero`/`CaseStudyBackLink` components recommended above.
